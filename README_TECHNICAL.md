# Technical Overview

This repository implements a small, end-to-end data analytics workflow in Python. The project is centered around a local e-commerce and logistics dataset that is generated, transformed, stored in SQLite, and visualized through a Streamlit dashboard.

The codebase is intentionally compact and local-first. There is no distributed architecture, no authentication layer, no REST API service, and no Docker deployment setup. Instead, the project emphasizes a clear data engineering flow and a portfolio-friendly demonstration of Python, pandas-based data transformation, SQL persistence, and analytics UI development.

## Architecture

```mermaid
flowchart TD
    A[run_full_project.py] --> B[generate_project_data()]
    A --> C[generate_logistics()]
    B --> D[export_to_sql()]
    C --> D
    D --> E[export_power_bi_dataset()]
    E --> F[dataset_power_bi.csv]
    D --> G[export_raw_csvs_for_etl()]
    G --> H[ventas.csv / productos.csv]
    H --> I[03_etl_pipeline.py]
    I --> J[extract_data()]
    J --> K[transform_data()]
    K --> L[load_data()]
    L --> M[ecommerce_portfolio.db]
    F --> N[app.py]
    N --> O[Streamlit dashboard]
```

### Component responsibilities

- `run_full_project.py`
  - Generates the synthetic business dataset.
  - Produces the base SQL tables used for analytics.
  - Writes Power BI-ready output and ETL source CSV files.
  - Invokes the ETL script as a final step.

- `03_etl_pipeline.py`
  - Extracts source CSVs when present.
  - Uses a sample-data fallback when source files are missing.
  - Cleans and derives business metrics.
  - Loads only new rows into the SQLite target table.

- `app.py`
  - Reads `dataset_power_bi.csv`.
  - Applies dashboard filters.
  - Produces KPI cards and Plotly charts.
  - Exposes a CSV download for filtered data.

- `config.py`
  - Centralizes file paths and dashboard color configuration.

## Backend

There is no framework-based backend service in this repository. The backend behavior is implemented as Python scripts performing batch ETL and local file-based data operations.

### Backend responsibilities

- Data synthesis and generation
- Data cleaning and validation
- SQL persistence
- Derived metric calculation
- Local execution orchestration
- Logging for ETL process state

### Observed backend patterns

- Direct use of `pandas` for tabular processing
- SQLite access through the Python standard library `sqlite3`
- Explicit exception handling in ETL stages
- Logging via Python's `logging` module
- Idempotency checks before inserts

## Frontend

The frontend is not a traditional web application. It is a Streamlit dashboard built in `app.py`.

### Frontend characteristics

- Single-page dashboard UI with sidebar filters
- KPI cards using `st.metric`
- Plotly charts for visual analysis
- Data table preview with CSV export
- Styling defined directly in the Python file via HTML/CSS injection

### Data handling in the UI

The dashboard loads the dataset through `pd.read_csv(config.POWER_BI_FILE)`, normalizes missing values, filters by `turno`, `estado_despacho`, and `categoria`, and then renders visualizations based on those filtered records.

## Data Flow

### Input → processing → business logic → output

```mermaid
flowchart LR
    A[Raw sales and product records] --> B[generate_project_data()]
    B --> C[Clean and merge tables]
    C --> D[Compute revenue and logistics fields]
    D --> E[Write SQLite tables]
    E --> F[Export Power BI dataset]
    F --> G[Streamlit dashboard filters and charts]
```

### Concrete transformation steps

1. Sales and product records are created with controlled randomness.
2. Duplicate rows are removed.
3. Invalid quantities are filtered out.
4. Null payment values are replaced with `No Especificado`.
5. Product metadata is joined to sales records.
6. `ingreso_total` is computed as `cantidad * precio_unitario`.
7. Logistics fields such as `tiempo_preparacion_min`, `estado_despacho`, and `kpi_semaforo_sla` are attached.
8. Resulting tables are exported to SQL and CSV for downstream analysis.

## Error Handling

The code includes explicit logging and exception handling in the ETL sequence.

### Observed patterns

- `logging.basicConfig(...)` in `03_etl_pipeline.py` writes execution logs to `pipeline_ejecucion.log`.
- `try/except` blocks wrap extraction, transformation, and load operations.
- `logging.exception(...)` records stack traces when failures happen.
- `logging.critical(..., exc_info=True)` is used for pipeline-level failures.
- Data quality checks are handled before persistence, including invalid quantity filtering and null replacement.

### Notable behavior

- If the required CSV files are missing, the ETL falls back to generated sample records instead of crashing.
- The loader checks for existing `id_venta` values before appending rows, which reduces duplicate persistence risk.

## Performance Considerations

Performance is not a major design constraint in this repository because the data volumes are modest and the application is local-first.

### Evidence-based observations

- Data operations rely on pandas DataFrame transformations, which are efficient for the project size.
- SQLite is used for local persistence rather than a server-based database.

## Engineering Decisions

### Decision: local CSV + SQLite-based ETL

- Reason: the repository is designed to be self-contained and portfolio-friendly.
- Trade-off: this keeps the project simple and easy to run locally, but it is not a production-grade distributed architecture.

### Decision: sample-data fallback in `extract_data()`

- Reason: the ETL should not fail immediately if raw CSV files are absent.
- Trade-off: the fallback is useful for local execution, but it intentionally does not persist synthetic data into the production database.

### Decision: idempotent loading via duplicate `id_venta` detection

- Reason: rerunning the pipeline should not create duplicate rows in the target table.
- Trade-off: this introduces a clear business-key check, but the logic is tightly coupled to the specific dataset schema.

### Decision: Streamlit for reporting

- Reason: the dashboard can be launched with a minimal command and directly consumes generated CSV output.
- Trade-off: it is fast to prototype but limited compared with a full frontend application framework.

### Decision: configuration centralized in `config.py`

- Reason: it avoids hardcoded path duplication across the codebase.
- Trade-off: configuration remains simple and local, but not environment-aware.
